# KMHTO — сервер совместной работы (этап 1)

Сервер-**арбитр** над расписанием ТО/КМХ. Клиент присылает не «новое значение», а
**операцию** и `baseVersion`; сервер сверяет права роли и версию и применяет либо
отклоняет правку.

## Требования

- **Node.js 22+** (используются встроенные `node:sqlite` и глобальный `WebSocket`
  для тестов). Внешних зависимостей нет — `npm install` не нужен.

## Запуск

```bash
node server/index.js
# [KMHTO] сервер 1.0.0 слушает ws://127.0.0.1:8787
# [auth] создан администратор по умолчанию: логин "admin", пароль "..."
```

После запуска **приложение доступно по адресу** `http://127.0.0.1:8787/` — сервер
раздаёт `app_kmhto.html` сам, и тогда запросы к `/login` идут с того же origin
(CORS не нужен). Открывать файл напрямую тоже можно — CORS-заголовки сервер отдаёт.

Пароль админа при первом запуске печатается в консоль. Пользователи:

```bash
node server/adduser.js alice secret specialist "Алиса"
node server/adduser.js bob   secret manager    "Боб"
node server/adduser.js vera  secret viewer     "Вера"
```

## Роли и права

Права задаются **по видам операций** (а не по «ячейкам A1/B2») — это соответствует
предметной области. Роль берётся **только из подписанного токена**; поля
`user`/`role` из сообщений игнорируются.

| Роль | Приоритет | Что может |
|---|---|---|
| viewer | 0 | только чтение |
| specialist | 300 | добавлять, переносить, менять вид, переставлять, комментарии |
| manager | 600 | то же + удаление, планирование, выходные |
| admin | 999 | всё + загрузка расписания и настройка ролей |

Порог для каждой операции лежит в `server/roles.js` (`DEFAULT_PERMISSIONS`) и
меняется админом на лету через `save_settings` (сохраняется в БД).

## Протокол

HTTP:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/` или `/app` | само приложение `app_kmhto.html` |

| GET | `/info` | описание |
| OPTIONS | `*` | preflight для входа из файла (CORS) |

| `op` | C→S | `{op:{opId,kind,eqId,eqIds,from,to,baseVersion,year,comment}}` |

## Управление пользователями

Администратор может управлять учётными записями **из приложения**: вкладка
«Сеть» → блок «Пользователи» → список, добавление, назначение роли, смена пароля,
удаление. Те же действия доступны из консоли (`server/adduser.js`).

Ограничения на сервере:

- команды принимаются только от роли `admin`;
- логин: 3–32 символа (латиница, цифры, `. _ -`), пароль — от 6 символов;
- удалить самого себя и последнего администратора нельзя;
- роль и существование пользователя перечитываются из `users.json` при каждой
  проверке токена, поэтому смена роли и удаление действуют **сразу**, без перевыпуска
  токена и перезапуска сервера.

## Виды операций

`add_work`, `move_work`, `change_type`, `move_and_type`, `delete_work`,
`swap_days`, `swap_types`, `plan_interval`, `plan_rule`, `plan_generate`,
`holiday`, `note`, `metrology`,
а также служебные `set_state`, `save_settings`.

Сервер применяет операцию к **своей** модели (`server/model.js`), после чего
возвращает авторитетную строку оборудования — клиент приводит её к серверному виду.

## Арбитраж версий (CS-модель)

1. Нет прав на вид операции → `op_rejected`.
2. `baseVersion` не указана → `op_rejected` (правка «вслепую» запрещена).
3. `baseVersion > версии сервера` → `op_rejected`.
4. `baseVersion == версии сервера` → применяется, статус `approved`.
5. `baseVersion < версии сервера`, но приоритет роли автора **выше** приоритета
   роли, сделавшей последнюю правку → применяется, статус `overridden`.
6. Иначе → `op_conflict` с текущим состоянием строки.

## Хранилище

SQLite (`node:sqlite`), файл `data/collab.db`:
`equipment` (состояние + версия + автор последней правки), `oplog` (журнал операций),
`doc` (праздники, заметки, версия документа, настройки ролей).

## Тесты

```bash
node tools/test_server.js
```

Поднимает сервер на свободном порту во временном каталоге и проверяет: логин,
подделку роли, права ролей, конфликт версий, перебивание старшим приоритетом,
рассылку, presence, синхронизацию, смену прав админом, heartbeat и перезапуск с
сохранением состояния — 42 проверки.


## Клиент (app_kmhto.html, вкладка «Сеть»)

Приложение остаётся автономным: без подключения `commitOp` выполняет правку
локально и пишет её в свой журнал. При подключении та же операция уходит на сервер.

1. Открыть приложение: `http://127.0.0.1:8787/` (лучше всего) или `app_kmhto.html`
   как файл. Вкладка **«Сеть»** → адрес сервера (`ws://127.0.0.1:8787/ws`; можно
   писать и просто `127.0.0.1:8787`), логин, пароль → «Подключиться».
   Токен выдаёт `POST /login`.
2. Сервер присылает `init`: пользователя, роли, права, список онлайн и состояние
   расписания. Строки сопоставляются по `id` оборудования.
3. Админ кнопкой **«⬆ Загрузить расписание на сервер»** отправляет текущий график
   (`set_state`) — так сервер получает исходные данные.
4. Каждая правка: локально применяется сразу (оптимистично) и уходит на сервер как
   операция. Ответ сервера:
   - `op_applied` — строка заменяется авторитетной версией сервера;
   - `op_conflict` — локальная правка откатывается, показывается, кто изменил запись;
   - `op_rejected` — правка откатывается, показывается причина (права, версия).
5. Роль проверяется и в клиенте (чтобы не делать заведомо отклоняемую правку), и на
   сервере (это и есть настоящая защита).
6. Presence: список онлайн с цветом роли; переподключение с нарастающей задержкой;
   `ping` каждые 20 секунд.
7. Праздники синхронизируются как документная операция `holiday`.

Индикатор состояния — чип в шапке («○ офлайн» / «● имя (роль)»).

## Безопасность

- Пароли — `scrypt` с индивидуальной солью; токены — HMAC-SHA256 с сроком жизни.
- Роль всегда читается из файла пользователей при проверке токена, поэтому смена
  роли действует немедленно и не требует перевыпуска.
- Веб-сокет без `hello` не допускает ничего, кроме `hello`/`ping`.
- Ограничения: сообщение ≤ 1 МБ, тело HTTP ≤ 64 КБ, задержка ответа при неверном
  пароле (против перебора).
- Для выхода за пределы localhost ставьте сервер за HTTPS/WSS-прокси.
